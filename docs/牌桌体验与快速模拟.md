# 牌桌体验与快速模拟

启动 `bun run web`，进入左侧 **牌桌体验**。如果 Web 服务在修改前已经启动，需要重启该服务并刷新页面。此功能使用本项目 `.env` 中的 lookup solver 配置，沿用实验的客户端；启动页面不会自动求解，点击开始、继续或单步才会执行。

## 使用方式

右侧为六个固定座位分别选择玩家配置，翻前、翻后使用该配置对应的 catalog 档位。默认六人、每人 100BB、0.5/1BB，无前注、抓注或抽水。庄家每手顺时针移动，物理座位与玩家配置保持对应。

- **观看模式**：六个圆形玩家头像围绕椭圆牌桌，旁边显示底牌，下方仅显示玩家类型和剩余筹码；当前行动者与赢家通过头像高亮区分。支持发牌、出牌和筹码移动动画。
- 牌桌中央显示“当前手数 / 目标手数”，持续运行显示“不限”。头像左上角使用统一的小型英文位置标识（BTN / SB / BB / UTG / HJ / CO），不重复中文位置或 D 标记。行动状态叠在圆形头像内部下半部，仅显示未行动、待行动、已弃牌、过牌、跟注、下注、加注或全下，不重复金额。本街累计投入以筹码图标加金额朝桌心摆放；结算后同一区域显示获奖金额，派奖飞向该区域。弃牌仅灰化头像图案、底牌和信息牌，位置与“已弃牌”文字保持清晰。完整行动金额仍保留在按手牌展开的历史详情与原始记录中。
- **主池与边池**：中央分别显示主池、边池 1、边池 2 等金额，以及合计金额。全下玩家以累计投入为限争夺对应底池；弃牌筹码保留在池内但不参与获奖，普通加注和不同的弃牌投入不会额外制造边池。当前尚未被跟注的超额投入单列为“待跟注”，下注轮结束后未匹配的部分显示“待退回”，不会派给其他玩家。展开底池明细可看各池的争夺资格和实际派奖。
- **派奖动画**：结算先保存，再按主池、各边池顺序，向该池对应赢家飞出筹码，平局则分别飞向多位赢家，并逐池更新界面中的筹码数。观看模式为每池预留约 1.1 秒，完成后再进入手间等待。快速模式不等待；底层筹码只结算一次，动画不修改牌局、统计或原始记录。已结算手牌可点击“重播本手派奖”，不请求 solver。系统减少动态效果时直接显示最终结果。
- **行动延迟**：轮到当前玩家时开始计时，同时请求 solver；响应和延迟均完成后才行动。可选 1、3、5 秒等，支持自定义 0–60 秒。接口更慢时继续等待接口。动画开启另留约 450ms 展示上一步，不向模型传递“思考时间”。
- **自动下一手**：默认结算后等待 5 秒，可调整 0–60 秒。关闭后每手结算即暂停，点击继续进入下一手。
- **自动补充筹码**：只在下一手开始前，为筹码耗尽的座位补到 100BB。关闭时，遇到破产座位暂停，开启后可继续。补充金额单独记录，不计为赢利。
- **快速模式**：使用相同核心、发牌算法、solver 请求、概率抽样与统计，忽略全部动画、行动延迟和手间等待，只更新进度和聚合统计。仍然逐个请求 solver，未加入并行桌。
- **暂停**：不再推进；在途请求会先返回并落盘。恢复时复用已保存成功响应，不再次请求同一决策。单步推进一次动作、发公共牌、结算或开始下一手。结束体验为终态，保留全部记录。
- **保存设置**：玩家档位下一手生效；模式、等待和自动机制用于后续推进。当前手中的玩家快照不变。随机种子在本次体验中固定，更换种子需新建。

随机种子控制洗牌与按概率选择动作。同一配置、种子和相同 solver 响应可复现结果；第三方响应变化时不能保证结果相同。每次抽样使用整个动作概率分布，不固定选择最大概率动作。

## 共用核心与规则

`src/table/engine.ts` 为纯牌局核心，无网络、DOM、动画或计时器。`src/runner/table.ts` 负责节奏、请求编排、检查点和恢复；`src/client/table-solver.ts` 构造 lookup 数据、校验策略档位与候选动作、抽样；`src/analysis/table-stats.ts` 聚合统计；`src/web/table.ts` 和 CSS 仅呈现快照。

核心处理盲注、四条街的行动顺序、最小加注、不足额全下的重新加注权限、未被跟注金额退回、主池与边池、七张选五张比牌、平分底池和零头筹码。每个边池独立比较，零头从庄家左侧起分配；每一步检查筹码守恒。每次请求前从初始种子重放当前手，防止损坏的检查点进入接口。

底池划分与逐池分配由 `src/table/pots.ts` 共用，派奖显示由 `src/web/table-payout.ts` 独立处理。具有相同争夺资格的弃牌投入层合并后再处理平局零头，避免同一主池的零头被重复分配；旧已结算记录仅合并展示，其原先保存的奖金不变。规则参考 [Poker TDA 的边池与零头筹码规则](https://www.pokertda.com/view-poker-tda-rules/)。

请求将当前庄家旋转到第三方约定的 BTN=0、SB=1、BB=2；仅携带当前行动者底牌，其他玩家底牌不发送。加注与全下金额为本街累计投入，跟注历史金额沿用接口约定的 0。翻前、翻后按当前行动者分别选择对应档位；不把所有玩家类型作为额外提示词发送。单次决策仍依赖第三方 solver 对当前行动者档位的解释，并非对手全信息的多人联合均衡求解。

HTTP 错误、档位未匹配、概率无效或任何正概率动作不合法时暂停，保存原文与原因。不会静默过滤错误动作或随机代打。牌桌只依赖概率执行，允许响应缺少 EV，原始 EV 不补造；实验报告的 EV 校验规则不变。

## 统计口径

仅结算完整手牌后计入统计，可按位置、固定座位、玩家类型及翻前/翻后档位查看，并导出 CSV。

三种分组都只统计当前选中的体验 Session，不包含其他 Session，也不计尚未结算的手牌。按位置（BTN、SB、BB 等）汇总会随庄家每手轮转，包含不同固定座位的玩家；按固定座位汇总则跟随同一座位跨位置累计，因此两表对应行的百分比不要求相同。三种分组共用累计函数和比例公式，原始计数总和一致，不能简单平均各行百分比。

各表的玩家类型列展示结算时的配置快照及该类型的已发牌手数，悬停查看翻前/翻后档位；中途调整玩家类型不会改写之前手牌的类型。VPIP/PFR 下方展示实际分子与分母。旧 Session 从本地完整结算日志只读补齐类型信息，并与原统计逐项核对；缺失或不一致时保留原统计并提示无法核实，不套用当前配置，不重新调用 solver。CSV 包含 Session、已结算手数和玩家类型样本组成。

| 指标 | 分子 | 分母 |
| --- | --- | --- |
| VPIP | 本手翻前主动投入过筹码的次数标记，每手最多一次 | 实际获得翻前行动机会的手数 |
| PFR | 本手翻前加注过的次数标记，每手最多一次 | 实际获得翻前行动机会的手数 |
| AF | 翻后下注次数 + 加注次数 | 翻后跟注次数 |
| WTSD | 看过翻牌且最终未弃牌参加摊牌的手数 | 看过翻牌的手数 |

盲注不算主动投入；BB walk 与被迫盲注全下而没有行动机会的手牌不计 VPIP/PFR 分母。AF 不包括过牌、弃牌；跟注为 0 且存在主动动作时显示 ∞，无样本显示 —。净赢为结算筹码减去本手初始筹码，所有座位净赢之和为 0。目录中的标称 VPIP/PFR/AF/WTSD 是目标风格说明，不保证有限样本与实际牌桌观测相等。

## 保存与恢复

牌桌记录默认位于 Git 忽略的 `artifacts/workbench/table-runs/<id>/`，与既有实验缓存分开，不改变旧格式。

- `checkpoint.json`：配置、当前手、牌堆、聚合统计、最近 20 手和有界行动记录。每步原子更新。
- `pending-decision.json`：最近一次完整请求、原始响应、抽样动作、耗时及错误。先保存后推进。
- `logs/hands-000000.jsonl` 等：每 1000 手一个分片，追加保存每次请求与原始响应、结算、边池、退款、玩家配置和底牌。重启复用会记录 `reused`，审计时按 `requestId` 去重；恢复窗口可能出现重复日志，统计以检查点为准。

页面下方“体验记录”统一查看；“最近结算与完整原始日志”可查看最近响应和全部日志分片。刷新只读取状态。关闭浏览器不停止服务端任务；服务重启后显示中断，必须显式继续。接口请求已发出但尚未保存时若进程被强制结束，无法保证第三方是否已执行，恢复可能再次调用。

“最近行动”先显示最近 20 手的编号、结算状态和公共牌，展开任意一手后查看六个固定座位当手的位置、玩家类型、两张底牌及净赢，并按发生顺序展示分街行动。每条玩家行动也附带该位置的底牌。刷新与实时进度更新会保留按手牌编号展开的状态。历史详情仅在展开时流式读取本地日志，不扩大快速模拟检查点中的历史快照。新日志直接保存事件列表；旧日志使用相同牌局核心从已保存的决策恢复，并与结算快照校验，不改写旧缓存、不重发 solver 请求。

## 速度与验证边界

快速模式目标允许 **1–100,000,000 手**。这只是目标上限，不代表已验证一亿手吞吐或具备离线 solver。实际速度受每次第三方响应、限流、网络和每步存盘影响；完整原始日志也会随请求数量增长。没有为了提速省略响应存档或使用另一个简化牌局引擎。

本次验证包括：本机模拟 solver 的观看/快速结果一致、在途暂停恢复不重复请求、轮转与底牌隔离、非法响应暂停、策略概率抽样、短全下与边池、平分零头；另执行 **10,000 手纯核心随机合法动作压力校验**，检查每步筹码守恒、52 张牌不重复及总盈亏为零。后者没有调用 solver，不能用于推断真实 AI 风格或第三方端到端速度。未自动运行正式付费对战。
