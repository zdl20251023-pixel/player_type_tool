固定 6 人桌、每人初始 100BB、无前注、无抓注，对应 `2-0 / 4-6p`。直接构造 100 条独立决策历史：翻前 50 条，翻后 50 条（翻牌 24、转牌 16、河牌 10），与场景设计文档编号一一对应。不启动牌桌服务，不执行玩家策略钩子，不修改业务代码。

## 运行

在 backend-framework 根目录执行：

```powershell
# 校验全部历史并保存计划，不加载客户端或请求网络
bun run test:ai:profiles --dry-run

# 100 条 × 3 种风格 × 默认重复 2 次 = 600 次真实请求
bun --env-file=.env.game run test:ai:profiles

# 只测试一条历史
bun --env-file=.env.game run test:ai:profiles --scenario P10 --repeat 3

# 本地算法和历史合法性测试，不调用第三方
bun test --isolate test/3rd_party/AI/lookup-profile-compare.test.ts
```

`--repeat` 支持 1..10，默认 2。可用 `--help` 查看参数。已有进程环境设置 `AI_SERVICE_URL` 时可省略 env-file；服务地址、代理、超时均复用项目 AI 客户端。普通 `bun run test` 不触发真实请求。

## 缓存、断点续跑与离线重建

**优化样式时只执行 `--render-only`，不要重新运行无参数的真实测试命令。**

```powershell
$resultDir = 'artifacts/lookup-profile-compare/<实际 run-id>'

# 不需要 AI_SERVICE_URL，不加载 AI 客户端，不发起网络请求
bun run test:ai:profiles --render-only $resultDir

# 实验中断时：成功及失败缓存都复用，只请求没有落盘的条目
bun --env-file=.env.game run test:ai:profiles --resume $resultDir

# 只有确实需要重试失败请求时使用；成功缓存仍不会重新请求
bun --env-file=.env.game run test:ai:profiles --resume $resultDir --retry-failed
```

离线重建使用缓存中的场景和请求快照。缺失响应在 HTML 中标为数据不足，不补零、不自动补请求；缓存与计划不一致或成功响应损坏时中止，不静默重新查询。临时目录下的缓存请保留到报告确认完成，清理后无法离线重建。

HTML 不依赖网络字体、CDN、fetch 或运行中的服务器；复制单个 HTML 仍可浏览所有派生内容，原始 JSON 链接需要保留同目录响应文件。HTML 内嵌数据做 script 结束标签转义，页面输出做 HTML 转义。

本地测试额外覆盖 `lookup-profile-cache.test.ts`：无 AI URL 时离线重建及全缓存续跑、损坏缓存拒绝复用、缺失样本处理、嵌入内容转义、结构化场景与设计文档的编号/牌张/位置一致性。

## 场景与合法性

`fixtures.ts` 保存 P01..P50、F01..F24、T01..T16、R01..R10 的结构化语义历史，`scenarios.ts` 将其转换为请求并提供风格映射。座位 BTN=0、SB=1、BB=2、UTG=3、HJ=4、CO=5，100 筹码=1BB。初始筹码为扣盲前的 10000；Raise 金额为本街加注到的总额，Call 编码 amount=0。底牌只设置在当前待决策玩家上。

翻前覆盖 UTG/CO/BTN/SB 开池、BB 防守、SB 面对开池、BTN 面对开池及跟注、UTG 面对 3bet；翻后覆盖顶对、弱成牌、听牌、暗三条、持续下注、转牌二次下注、河牌抓诈唬和未成听牌。

`validate.ts` 在发请求前逐条重放，检查座位与初始筹码、行动顺序、最小下注/加注、筹码余额、下注轮闭合、街道推进、牌张编码与重复，以及历史是否正好截止到 Hero 决策。它只支持本实验使用的非 all-in、完整加注历史；不替代生产牌桌引擎。候选解可以含全下动作。

同一历史的三种请求仅改变 `strategy_profile` 和追踪 ID，始终省略 `request_profile`，固定普通 lookup 的协议、菜单和阈值等参数。每轮先请求 GTO 作为基线，再请求另外两种风格。这里改变的是决策玩家的风格，并未设置全桌六人的风格；固定历史也不要求三种风格此前必然采取相同行动。

## 输出

每次保存到 Git 已忽略的 `artifacts/lookup-profile-compare/<run-id>/`：

- `session.json`：实验时间、重复次数、完整场景快照和固定请求计划，重建报告不依赖后续修改过的场景代码。
- `plan.json`、`validation.json`：请求计划和历史重放后的底池、待跟注金额、剩余筹码。
- 各请求 JSON：请求体、完整响应、耗时、错误信息；不序列化 Axios 配置或认证信息。
- **`report.html`：优先阅读，正式自包含报告，包含总体结论、侧栏快捷跳转、街道/位置/类型/结论筛选、弃/跟/过/主动汇总、牌面、行动时间线及候选概率/EV。**
- `conclusion.md`：100 条行动线的三种风格概率、实际推荐和分阶段均值。
- `summary.md`：增加每条行动线的底池、底牌、各次最高概率动作/实际推荐、档位匹配及所有候选动作的概率和 EV。
- `report.md`、`report.json`：逐次对 GTO 的结构、概率和 EV 差异，以及同档位重复波动。

每次请求完成后先将完整原始结果原子落盘，再更新 `progress.json`；全部处理结束后生成派生的 HTML 和 Markdown。HTTP 200 仍检查错误字段、非空策略、有效概率/EV、重复动作；风格档位还必须回显匹配成功。GTO 回显 gto 或 no_profile_applied 均按均衡基线处理。任一失败继续其余请求并最终以 1 退出，失败不等价于无差异。

## 如何判断风格

报告按动作类型、金额、底池比例、座位对齐完整候选，比较概率（百分点）、EV、菜单数量及字段类型。新增/删除动作的概率按 0 对齐，缺失 EV 不补 0；菜单顺序变化不当作结构变化。

方向检查使用相对 GTO 的概率，而不是单次抽样推荐：翻前检查松弱更多继续且少主动、紧凶更少继续且继续后的主动比例更高；继续概率低于 1% 时不使用条件主动比例作反向判断，避免极小分母和浮点舍入误报。翻后检查松弱主动率更低、紧凶更高。容差为 0.5 个百分点，输出符合预期、存在反向变化、差异不明显或数据不全。最高概率动作与接口 suggested_action 分开列出。此检查是有限样本的相对方向检查，不是风格认证；样本均值也不是玩家真实 VPIP/PFR。
